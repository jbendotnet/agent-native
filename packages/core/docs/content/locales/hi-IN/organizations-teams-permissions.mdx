# संगठन, टीमें और अनुमतियाँ

संगठन team membership और tenant boundary तय करता है। Workspace apps और deployment config को समूहित करता है, लेकिन संगठन का विकल्प नहीं है। Server को permissions जाँचनी चाहिए। UI में button छिपाना authorization नहीं है।

## भूमिकाओं के तीन दायरे

- संगठन के `owner`, `admin` और `member` roles टीम प्रबंधन नियंत्रित करते हैं। मालिक और एडमिन ईमेल डोमेन से अपने-आप जुड़ना मैनेज करते हैं; ऐप्स के बीच साझा A2A secret सिर्फ़ मालिक मैनेज करता है।
- App roles एक app के भीतर की क्षमताएँ नियंत्रित करते हैं। किसी सदस्य के कई app roles हो सकते हैं।
- Resource roles `viewer`, `editor` और `admin` एक row तक पहुँच नियंत्रित करते हैं।

App code में roles और permission keys घोषित होते हैं। Admin टीम पेज से सदस्य के पूरे role set को बदल सकता है और घोषित permissions को roles से जोड़ सकता है। Override न होने पर app defaults लागू होते हैं। Invitation में app roles पहले से दिए जा सकते हैं। App admin को organization admin अधिकार नहीं मिलते।

आमंत्रण और config के लिए [प्रशासित डिप्लॉयमेंट](/docs/administered-deployments) देखें। डेटा पहुँच के लिए [डेटा स्कोपिंग](/docs/security#data-scoping) देखें।

## वैकल्पिक अनुमति नीतियाँ

डिफ़ॉल्ट रूप से अनुमति जाँच के लिए असाइन की गई ऐप भूमिका आवश्यक है। `defineAppRoles` का वैकल्पिक दूसरा आर्ग्युमेंट सर्वर पर यह नीति बदलता है। Forms यह उपयोग करता है:

```ts
const formsAccess = defineAppRoles(
  {
    appId: "forms",
    roles: ["editor", "reviewer"] as const,
    defaultRole: "editor",
    permissions: {
      "forms.edit": ["editor"],
      "forms.review": ["editor", "reviewer"],
    },
  },
  { unassignedRole: "editor", allowOrgAdmins: true },
);
```

- `unassignedRole` बिना ऐप भूमिका असाइनमेंट वाले सक्रिय सदस्यों को घोषित भूमिका की अनुमतियाँ देता है। अनुमति ओवरराइड अब भी लागू होते हैं। यह असाइनमेंट नहीं बनाता और हटाए गए सदस्यों या केवल बंद की गई भूमिकाओं वाले असाइनमेंट पर लागू नहीं होता। सभी असाइनमेंट साफ़ करने से यह डिफ़ॉल्ट व्यवहार फिर लागू होता है।
- `allowOrgAdmins: true` संगठन के सक्रिय मालिकों और एडमिन को उनकी ऐप भूमिकाओं या अनुमति ओवरराइड की परवाह किए बिना किसी भी घोषित ऐप अनुमति की जाँच पास करने देता है। यह ऐप एडमिन को संगठन के प्रशासन का अधिकार नहीं देता।

ये विकल्प केवल `requirePermission` और `assertPermission` को प्रभावित करते हैं। `resolve`, `requireAny` और `assertAny` स्पष्ट असाइनमेंट का उपयोग करते रहते हैं; `defaultRole` केवल प्रदर्शन के लिए है। विकल्प छोड़ने पर सख्त नीति बनी रहती है। कोई भी विकल्प संसाधन प्राधिकरण का स्थान नहीं लेता: `accessFilter` और `assertAccess` जाँच बनाए रखें।

Forms मौजूदा बिना भूमिका असाइन किए गए सदस्यों की संपादन पहुँच बनाए रखता है। स्पष्ट रूप से असाइन किया गया Reviewer सबमिशन की समीक्षा कर सकता है, लेकिन फ़ॉर्म संपादित नहीं कर सकता; Editor दोनों कर सकता है। संसाधन साझाकरण अब भी तय करता है कि वे किन फ़ॉर्म और सबमिशन तक पहुँच सकते हैं।

संगठन के स्वामित्व वाले फ़ॉर्म को संपादित करने और सबमिशन की समीक्षा करने के लिए उस फ़ॉर्म के संगठन की सक्रिय सदस्यता आवश्यक है, जब तक कि साझाकरण प्रणाली कॉलर को फ़ॉर्म का मालिक न माने। केवल सीधे साझा किए जाने से यह ऐप अनुमति जाँच पास नहीं होती।

## उपयोगकर्ता समूह {#user-groups}

किसी संगठन में उसके मौजूदा सदस्यों के पुन: उपयोग योग्य समूह हो सकते हैं। मालिक और एडमिन समूह की सदस्यता संभालते हैं, और एक व्यक्ति कई समूहों में हो सकता है। ऐप किसी समूह का उपयोग ऐसे संसाधन को साझा करने के लिए कर सकते हैं जो समूह साझाकरण का समर्थन करता हो, या वर्कस्पेस कनेक्शन तक पहुँच सीमित करने के लिए कर सकते हैं।

नया समूह सामान्य एक्सेस सूची होता है। उसे टीम बनाने के लिए `upsert-workspace-user-group` में स्पष्ट रूप से `isTeam: true` दें। मौजूदा समूह का रूपांतरण उसका ID, सदस्य और संसाधन या कनेक्शन की अनुमति बनाए रखता है। अपडेट में `isTeam` छोड़ने पर समूह का प्रकार नहीं बदलता। सामान्य समूह में टीम संदर्भ या साझा बातचीत की खोज नहीं होती।

संगठन के मालिक और एडमिन टीम बना सकते हैं, उसका रूपांतरण या नाम बदल सकते हैं, उसे मिटा सकते हैं और लीड तय कर सकते हैं। लीड केवल अपनी टीम के सामान्य सदस्यों को जोड़ या हटा सकता है। वह लीड या संगठन के रोल नहीं बदल सकता। टीम का रोल किसी की निजी बातचीत की पहुँच नहीं देता।

### टीम संदर्भ {#team-context}

सक्रिय टीम हर उपयोगकर्ता और संगठन के लिए अलग सहेजी जाती है। `get-active-workspace-team` सहेजा चुनाव लौटाता है और सदस्यता फिर जाँचता है। `set-active-workspace-team` में `teamGroupId: null` निजी संदर्भ चुनता है। चुनाव केवल नई बातचीत पर लागू होता है। मौजूदा बातचीत की टीम बाइंडिंग नहीं बदलती। पुराने बिना बाइंडिंग वाले संवाद वैसे ही रहते हैं। चुनाव पहुँच की अनुमति नहीं है।

V1 में टीम के निर्देश, कौशल और मेमोरी उपलब्ध हैं। यह मनमाने ऐप डेटा का टीम स्वामित्व नहीं है। टीम संसाधन के लिए `scope: "team"` और `teamGroupId` आवश्यक हैं। सामान्य और बैकग्राउंड रन बातचीत की बंधी टीम का संदर्भ संगठन के बाद और निजी संदर्भ से पहले लोड करते हैं।

टीम मिटाने पर बंधी बातचीत, संदर्भ, निजी संसाधन और शेयर रिकॉर्ड बने रहते हैं, लेकिन आगे की पहुँच बंद हो जाती है। उसी नाम की नई टीम का नया ID होता है। पुराना डेटा उससे नहीं जुड़ता।

### टीम ऐक्शन {#team-actions}

| ऐक्शन                               | इनपुट                                                                   | परिणाम                                                                            |
| ----------------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `upsert-workspace-user-group`       | `id?`, `name`, `memberEmails?: string[] = []`, `isTeam?`, `leadEmails?` | समूह का `id`, `orgId`, `name`, `memberEmails`, `isTeam`, `leadEmails` और मेटाडेटा |
| `set-workspace-team-leads`          | `teamGroupId`, पूरी `leadEmails` सूची                                   | अपडेट किया समूह                                                                   |
| `bulk-update-workspace-user-groups` | `groupId`, 1–100 `memberEmails`, `operation: "add" \| "remove"`         | अपडेट किया समूह                                                                   |
| `list-workspace-user-groups`        | `{}`                                                                    | समूह। गैर-एडमिन को अपनी टीम के अलावा सदस्य और लीड की खाली सूचियाँ मिलती हैं       |
| `delete-workspace-user-group`       | `id`                                                                    | `{ id, deleted: true }`, समूह न मिलने पर त्रुटि                                   |
| `set-active-workspace-team`         | `teamGroupId: string \| null`                                           | `{ orgId, teamGroupId }`                                                          |
| `get-active-workspace-team`         | `{}`                                                                    | `{ orgId, teamGroupId }`                                                          |

मालिक या एडमिन टीम बना सकता है। उसे चुनने के लिए कॉलर का सदस्य होना भी आवश्यक है। उदाहरण के पते मौजूदा संगठन सदस्यों से बदलें।

```ts
import { callAction } from "@agent-native/core/client/hooks";

await callAction("upsert-workspace-user-group", {
  name: "Support",
  memberEmails: ["lead@example.com", "member@example.com"],
  isTeam: true,
  leadEmails: ["lead@example.com"],
});
```

मौजूदा समूह का रूपांतरण करते समय उसके सदस्य भेजें। `memberEmails` छोड़ने पर डिफ़ॉल्ट खाली सूची है। फिर कॉलर निजी संदर्भ चुन सकता है।

```ts
const groups = await callAction("list-workspace-user-groups", {});
const group = groups.find((group) => group.name === "Support");
if (!group) throw new Error("Support समूह नहीं मिला");

await callAction("upsert-workspace-user-group", {
  id: group.id,
  name: group.name,
  memberEmails: group.memberEmails,
  isTeam: true,
});
await callAction("set-active-workspace-team", { teamGroupId: null });
```

बातचीत निजी होती है। टीम शेयर केवल देखने की अनुमति देता है। [टीम बातचीत](/docs/sharing#team-conversations) देखें।

विवरण के लिए [Sharing & Privacy → Group grants](/docs/sharing#group-grants) और [Workspace Connections](/docs/workspace-connections) देखें.
