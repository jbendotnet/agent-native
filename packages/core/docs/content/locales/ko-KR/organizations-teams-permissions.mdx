# 조직, 팀 및 권한

조직은 팀 멤버십과 테넌트 경계를 정의합니다. 워크스페이스는 앱과 배포 설정을 묶지만 조직을 대체하지 않습니다. 권한은 서버에서 확인해야 합니다. UI에서 버튼을 숨기는 것은 접근 제어가 아닙니다.

## 세 가지 역할 범위

- 조직의 `owner`, `admin`, `member` 역할은 팀 관리를 제어합니다. 소유자와 관리자는 이메일 도메인 자동 참여를 관리하고, 앱 간 A2A 공유 시크릿은 소유자만 관리합니다.
- 앱 역할은 하나의 앱 안에서 가능한 작업을 제어합니다. 한 멤버가 여러 역할을 가질 수 있습니다.
- 리소스 역할 `viewer`, `editor`, `admin`은 한 행의 액세스를 제어합니다.

앱 코드에서 역할과 권한 키를 선언합니다. 관리자는 팀 화면에서 멤버의 전체 역할 집합을 교체하고 선언된 권한을 역할에 매핑할 수 있습니다. 재정의가 없으면 앱 기본값이 적용됩니다. 초대에 앱 역할을 미리 지정할 수도 있습니다. 앱 관리자는 조직 관리자 권한을 얻지 않습니다.

초대와 설정은 [관리 배포](/docs/administered-deployments), 데이터 액세스는 [데이터 범위 지정](/docs/security#data-scoping)을 참고하세요.

## 선택적으로 적용하는 권한 정책

기본적으로 권한 검사를 통과하려면 앱 역할이 할당되어 있어야 합니다. `defineAppRoles`의 선택적 두 번째 인수로 서버 정책을 바꿀 수 있습니다. Forms는 다음 설정을 사용합니다.

```ts
const formsAccess = defineAppRoles(
  {
    appId: "forms",
    roles: ["editor", "reviewer"] as const,
    defaultRole: "editor",
    permissions: {
      "forms.edit": ["editor"],
      "forms.review": ["editor", "reviewer"],
    },
  },
  { unassignedRole: "editor", allowOrgAdmins: true },
);
```

- `unassignedRole`은 앱 역할 할당이 없는 활성 구성원에게 선언된 역할의 권한을 적용합니다. 권한 재정의는 계속 적용됩니다. 역할 할당을 생성하지 않으며, 제거된 구성원이나 폐기된 역할만 포함하는 할당에는 적용되지 않습니다. 모든 할당을 지우면 이 기본 동작으로 돌아갑니다.
- `allowOrgAdmins: true`는 활성 조직 소유자와 관리자가 앱 역할이나 권한 재정의와 관계없이 선언된 앱 권한 검사를 통과하도록 합니다. 앱 관리자에게 조직 관리 권한을 부여하지는 않습니다.

이 옵션은 `requirePermission`과 `assertPermission`에만 영향을 줍니다. `resolve`, `requireAny`, `assertAny`는 명시적 할당을 사용하는 동작을 유지하며, `defaultRole`은 표시 전용입니다. 옵션을 생략하면 엄격한 정책이 유지됩니다. 어느 옵션도 리소스 권한 검사를 대체하지 않습니다. `accessFilter`와 `assertAccess` 검사를 유지하세요.

Forms는 역할이 할당되지 않은 기존 구성원의 편집 권한을 유지합니다. 명시적으로 할당된 Reviewer는 제출 내용을 검토할 수 있지만 폼을 편집할 수는 없습니다. Editor는 둘 다 할 수 있습니다. 접근 가능한 폼과 제출 내용은 계속 리소스 공유로 결정됩니다.

조직 소유 폼을 편집하거나 제출 내용을 검토하려면 해당 폼의 조직에 활성 구성원으로 속해 있어야 합니다. 단, 공유 시스템이 호출자를 폼 소유자로 인식하는 경우는 예외입니다. 직접 공유만으로는 이 앱 권한 검사를 통과할 수 없습니다.

## 사용자 그룹 {#user-groups}

조직은 현재 구성원으로 재사용 가능한 사용자 그룹을 만들 수 있습니다. 소유자와 관리자가 그룹 구성원을 관리하며, 한 사람이 여러 그룹에 속할 수 있습니다. 앱은 그룹 공유를 지원하는 리소스에 접근 권한을 주거나 워크스페이스 연결 사용자를 제한할 때 그룹을 사용할 수 있습니다.

일반 그룹은 접근 목록입니다. `isTeam: true`를 명시해야 팀으로 변환됩니다. 변환은 ID, 구성원, 리소스 및 연결 권한을 유지합니다. 업데이트에서 `isTeam`을 생략하면 기존 유형이 유지됩니다. 조직 소유자와 관리자는 팀 생성, 변환, 이름 변경, 삭제 및 리더 지정을 할 수 있습니다. 리더는 자기 팀의 일반 구성원만 변경합니다. 조직 역할이나 비공개 대화 접근 권한은 얻지 않습니다.

### 팀 컨텍스트와 대화 연결 {#team-context}

선택은 사용자와 조직별로 저장됩니다. `get-active-workspace-team`은 선택을 복원하고 검증합니다. `set-active-workspace-team`은 현재 팀 또는 개인 작업을 뜻하는 `null`을 선택합니다. 새 대화에만 영향을 줍니다. 기존 연결은 변경할 수 없으며 이전의 연결되지 않은 대화는 그대로 유지됩니다. 팀 선택은 접근 권한이나 공유를 부여하지 않습니다.

V1은 팀 지침, 스킬, 메모리만 지원하며 임의의 앱 데이터를 팀 소유로 만들지 않습니다. 리소스는 `scope: "team"`과 `teamGroupId`를 사용합니다. 전경과 배경 실행은 조직 컨텍스트 다음, 개인 컨텍스트 전에 연결된 팀의 컨텍스트를 읽습니다. 팀 삭제 시 연결된 대화, 컨텍스트, 개인 리소스, 공유 행은 보존되지만 해당 팀을 통한 접근은 종료됩니다. 같은 이름의 새 팀에는 새 ID가 부여됩니다.

### 팀 액션 {#team-actions}

| 액션                                | 입력                                                      | 결과                                                                                                           |
| ----------------------------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `upsert-workspace-user-group`       | `{ id?, name, memberEmails?: [], isTeam?, leadEmails? }`  | `id`, `orgId`, `name`, `memberEmails`, `isTeam`, `leadEmails` 및 메타데이터를 포함한 그룹. 구성원 기본값: `[]` |
| `set-workspace-team-leads`          | `{ teamGroupId, leadEmails }`                             | 업데이트된 그룹. 전체 리더 목록을 교체                                                                         |
| `bulk-update-workspace-user-groups` | `{ groupId, memberEmails, operation: "add" \| "remove" }` | 업데이트된 그룹. 이메일 1~100개                                                                                |
| `list-workspace-user-groups`        | `{}`                                                      | 그룹. 구성원과 리더 목록은 소유자, 관리자, 해당 팀 구성원에게만 표시                                           |
| `delete-workspace-user-group`       | `{ id }`                                                  | `{ id, deleted: true }`. 없으면 실패                                                                           |
| `set-active-workspace-team`         | `{ teamGroupId: string \| null }`                         | 구성원 자격 검증 후 `{ orgId, teamGroupId }`                                                                   |
| `get-active-workspace-team`         | `{}`                                                      | `{ orgId, teamGroupId }` 및 앱 상태에 선택 복원                                                                |

소유자나 관리자는 팀을 만들 수 있습니다. 선택하려면 자신도 구성원이어야 합니다:

```ts
import { callAction } from "@agent-native/core/client/hooks";

await callAction("upsert-workspace-user-group", {
  name: "Support",
  isTeam: true,
  memberEmails: ["lead@example.com", "member@example.com"],
  leadEmails: ["lead@example.com"],
});
```

기존 그룹 변환 시 구성원을 명시적으로 유지합니다. 이후 개인 작업으로 돌아갈 수 있습니다:

```ts
const groups = await callAction("list-workspace-user-groups", {});
const group = groups.find((group) => group.name === "Support");
if (!group) throw new Error("Support 그룹을 찾을 수 없습니다");

await callAction("upsert-workspace-user-group", {
  id: group.id,
  name: group.name,
  memberEmails: group.memberEmails,
  isTeam: true,
});
await callAction("set-active-workspace-team", { teamGroupId: null });
```

대화는 개인 소유이며 기본적으로 비공개입니다. 읽기 전용 공유는 [팀 대화](/docs/sharing#team-conversations)를 참조하세요.

자세한 내용은 [공유 및 개인정보 보호 → 그룹 공유](/docs/sharing#group-grants)와 [워크스페이스 연결](/docs/workspace-connections)을 참고하세요.
